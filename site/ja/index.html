エージェントは毎ターン、会話の全体を送り直します。

Portway は、変わった部分だけを送るローカル HTTP プロキシです。リンクの 反対側に Portway のレシーバーがあれば、各リクエストは直前のリクエストに対する差分として ネットワークを渡ります。セッションがどれだけ長く続いても、およそ 1 キロバイトです。

GitHub でソースを見る はじめに

40 ターン目は、39 ターン目に 4 キロバイトを足したもの

コーディングエージェントはサーバー側に何の状態も持ちません。もう一歩進むために、 システムプロンプトとこれまでのすべてのメッセージ、すべてのツール結果をもう一度送り、 そのあとに新しく増えた数キロバイトを付け足します。どのリクエストも、直前のリクエストを ほとんどそのまま写したものです。

つまりセッションのアップロード量は、長さの二乗で増えていきます。そのアップロードが 待ち時間や費用として返ってくる場所では、すぐに効いてきます：

  • 別リージョンにある自前のモデルサーバー、あるいは自分で運用するゲートウェイ、
  • 1 ターンごとに VPN や SSH のホップを渡るリモート開発マシン、
  • 遅い、共有された、あるいは従量制の回線につながったノート PC。

短い単発のリクエストではほとんど得るものがありません。基盤にできる 先行リクエストが存在しないからです。

直前のターンが辞書になる

Portway は 2 か所で動きます。エージェントの隣のセンダーと、呼び出し先の サービスの手前のレシーバーです。どちらも、最後に合意したリクエストボディを 保持します。センダーは次のリクエストをそれに対して圧縮し、レシーバーはサービスが 1 バイトでも見る前に元の姿へ戻します。

両端が基盤を合意するまで

  1. 1 ターン目が辞書の種を蒔きます。zstd で圧縮され、 X-Dict-Store: 1 とともに送られます。レシーバーはそれを解いて先へ渡し、 ボディを取っておきます。

  2. レシーバーは、取っておいたものを知らせます。応答には、実際に 保存したバイト列の SHA-256 を載せた X-Dict-Stored が付きます。センダーは そのハッシュが自分の複製と一致したときにだけ、そのボディを基盤として使います。

  3. 2 ターン目は 1 ターン目をハッシュで指名します。DCZ として送られ ます。辞書の SHA-256 を載せた 40 バイトのヘッダーに続けて、その辞書に対して圧縮され、 内容チェックサムで終わる zstd フレームが並びます。センダーはルートごとに確認済みの ボディを最大 8 つ保持し、新しいリクエストと最も長い接頭辞を共有するものを選びます。 追記だけの会話では、それが直前のターンです。

基盤が消えたときは、段階的に降ります

レシーバーが再起動する、古いボディを追い出す、あるいは初めて見るセンダーと出会う ことがあります。どれもリクエストを失敗させません。レシーバーは復元できないものを、 アプリケーションが動き出す前に拒み、拒否の印を残します。センダーはより少ない 圧縮でやり直します。

  1. 保存されたボディに対する DCZ 412 辞書が消えた場合、または 400・415 フレームが拒まれた場合に降ります
  2. 辞書なしの素の zstd 415 エンコーディングが拒まれた場合に降ります
  3. 非圧縮、エージェントが送ったそのまま 常に受け付けられます

リクエストは最大 3 回送られます。Portway が再生するのは、レシーバーの印が付いた拒否 だけです。レシーバーはその印をアプリケーションの応答から取り除くので、アプリケーション が再生を引き起こすことはなく、同じリクエストが 2 度実行されることもありません。 アプリケーションのエラーはそのままエージェントへ返ります。

1 ターンの代価は、そのターンが増やした分だけ

同じベンチマークを 4 つのコンテキストサイズで、それぞれ 20 ターンずつ。素の zstd は 各リクエストをおよそ 5 分の 1 に縮め、直前のターンの辞書はコンテキストの大きさに かかわらず、およそ 1 キロバイトを残します。

cargo build --release --locked
python3 scripts/bench.py --turns 20 --context-kb 1024

やらないこと

節約するのはバイト数であり、トークンではありません。
モデルが受け取るリクエストは同一で、課金されるトークンも同一です。プロバイダーの プロンプトキャッシュは繰り返される接頭辞を処理する費用を削り、Portway はそれを 送る費用を削ります。両方をお使いください。
レシーバーが必要です。
プロトコルを広告しない API に直接向けた場合、センダーはリクエストを圧縮せず そのまま転送します。レシーバーは portway receive か、プロトコルを 実装した任意のサーバーです。
再起動すると忘れます。
辞書は両端のメモリにしか存在せず、認証情報ごとに分かれています。既定では 32 KiB 未満のボディが辞書になることはありません。
話すのは素の HTTP/1.1 です。
WebSocket も CONNECT も HTTP/2 も受信側 TLS もありません。TLS と認証は手前の ゲートウェイに任せてください。リクエストは設定可能な 256 MiB まで バッファリングし、応答はストリーミングします。

試してみる

macOS か Linux で、Rust 1.97 以降と C ツールチェーンが必要です。プロバイダーも エンドポイントも認証情報も価格も、どれ一つとして組み込まれていません。

  1. チェックアウトからインストールします。ターミナルダッシュボードと ブラウザーコンソールも使うなら --features tui,web を付けます。

    git clone https://github.com/rath/portway
cd portway
cargo install --path crates/portway --locked

  2. サービスを指して起動します。

    # portway.toml
upstream = "https://api.example.com"
host = "127.0.0.1"
port = 8787
    portway --config ./portway.toml

  3. エージェントを Portway に向けます。API の base URL を http://127.0.0.1:8787/v1 にして、キーとモデル名はそのままにします。 Portway は Authorization ヘッダーをそのまま通し、自分では鍵を 持ちません。

  4. 反対側にレシーバーを置きます。サービスの手前のゲートウェイの 後ろで portway receive を動かし、センダーをそのゲートウェイに向けます。 レシーバーの設定 に手順があります。

同じリポジトリには、埋め込み可能な Rust ライブラリ portway-core と、 デーモンモード、レポート、ターミナルダッシュボード、ブラウザーコンソールを備えた CLI が 入っています。リクエストのメタデータだけを SQLite に記録し、ボディ、認証情報、 辞書の中身は決して記録しません。
