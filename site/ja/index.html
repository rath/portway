コーディングエージェントの通信量を削減。

Claude Code や Codex などのコーディングエージェントは、ターンごとに長くなる会話を丸ごと送り直します。Portway は直前のリクエストを基に次のリクエストを圧縮し、レシーバーまでの通信量を減らします。レシーバーは元のリクエストを復元してモデルに転送します。

brew install rath/tap/portway

macOS Apple シリコン · Linux x86_64 / ARM64

設定ガイド その他のインストール方法

インストールして、エージェントを接続

Homebrew でインストールして、エージェントを接続します。ターミナルダッシュボードとブラウザーコンソールが含まれており、Rust ツールチェーンは不要です。

  1. Portway をインストールします。macOS Apple シリコンと Linux x86_64 / ARM64（glibc 2.28 以降）に対応しています。

    brew install rath/tap/portway

    Homebrew を使わない場合は、リリースバイナリをダウンロードするか、ソースからビルドできます。Rust と C ツールチェーンが必要なのはソースからのビルドだけです。

  2. API のマウント設定を portway.toml に保存します。次にブラウザーコンソールとともに起動します：

    # portway.toml
host = "127.0.0.1"
port = 8787

[upstreams]
anthropic = "https://api.anthropic.com"
codex = "https://chatgpt.com/backend-api/codex"
    portway --config ./portway.toml --web

  3. エージェントを自分のマウントに向けます。変えるのはそれだけです。Claude Code は ANTHROPIC_BASE_URL=http://127.0.0.1:8787/anthropic、Codex はプロバイダー項目の base_url = "http://127.0.0.1:8787/codex" です。ログインもモデル名もそれぞれそのまま使い、Portway はリクエストに載った認証情報をそのまま通して、自分では鍵を持ちません。OpenAI 互換のサービスなら upstream ひとつと base URL http://127.0.0.1:8787/v1 で済みます。

  4. デルタ圧縮を使うにはレシーバーを追加します。サービスの手前にあるゲートウェイの後ろで portway receive を動かし、センダーをそのゲートウェイに向けます。レシーバーの設定に手順があります。

同じリポジトリには、埋め込み可能な Rust ライブラリ portway-core と、デーモンモード、レポート、ターミナルダッシュボード、ブラウザーコンソールを備えた CLI が入っています。リクエストのメタデータだけを SQLite に記録し、ボディ、認証情報、辞書の中身は決して記録しません。

40 ターン目は、39 ターン目に 4 キロバイトを足したもの

コーディングエージェントはサーバーに状態を持ちません。もう一歩進むために、システムプロンプトとこれまでのすべてのメッセージ、すべてのツール結果をもう一度送り、そのあとに新しく増えた数キロバイトを付け足します。どのリクエストも、直前のリクエストをほとんどそのまま写したものです。

つまりセッションのアップロード量は、長さの二乗に比例して増えていきます。アップロードが待ち時間や費用に直結する環境では、すぐに効いてきます：

  • 別リージョンの自前モデルサーバーや、自分で運用するゲートウェイ、
  • 1 ターンごとに VPN や SSH を経由するリモート開発マシン、
  • 低速・共有・従量制の回線につながったノート PC。

短い単発のリクエストではほとんど得るものがありません。基準にできる先行リクエストがないからです。

直前のターンが辞書になる

Portway は 2 か所で動きます。エージェントの隣のセンダーと、呼び出し先のサービスの手前のレシーバーです。どちらも、最後に合意したリクエストボディを保持します。センダーはそれを基準に次のリクエストを圧縮し、レシーバーはサービスが 1 バイトでも見る前に元の姿へ戻します。

両端が基準を揃えるまで

  1. 1 ターン目が辞書の種を蒔きます。zstd で圧縮され、X-Dict-Store: 1 とともに送られます。レシーバーはそれを解いて先へ渡し、ボディを取っておきます。

  2. レシーバーは、何を取っておいたかを知らせます。応答には、実際に保存したバイト列の SHA-256 を載せた X-Dict-Stored が付きます。センダーはそのハッシュが自分の複製と一致したときにだけ、そのボディを基準として使います。

  3. 2 ターン目は 1 ターン目をハッシュで指定します。DCZ として送られます。辞書の SHA-256 を載せた 40 バイトのヘッダーに続けて、その辞書を基準に圧縮され、内容チェックサムで終わる zstd フレームが並びます。センダーはルートごとに確認済みのボディを最大 8 つ保持し、新しいリクエストと最も長い接頭辞を共有するものを選びます。追記だけの会話では、それが直前のターンです。

基準が消えたときは、一段ずつ降ります

レシーバーが再起動する、古いボディを追い出す、あるいは初めて見るセンダーと出会うことがあります。どれもリクエストを失敗させません。レシーバーは復元できないものを、アプリケーションが動き出す前に拒み、拒否のマーカーを残します。センダーは圧縮を弱めてやり直します。

  1. 保存されたボディを基準にした DCZ 412（辞書が消えた）、400・415（フレームが拒まれた）なら降ります
  2. 辞書なしの素の zstd 415（エンコーディングが拒まれた）なら降ります
  3. 非圧縮、エージェントが送ったそのまま 常に受け付けられます

リクエストは最大 3 回送られます。Portway が再送するのは、レシーバーのマーカーが付いた拒否だけです。レシーバーはそのマーカーをアプリケーションの応答から取り除くので、アプリケーションが再送を引き起こすことはなく、同じリクエストが 2 度実行されることもありません。アプリケーションのエラーはそのままエージェントへ返ります。

1 ターンのコストは、そのターンが増やした分だけ

同じベンチマークを 4 つのコンテキストサイズで、それぞれ 20 ターンずつ。素の zstd は各リクエストをおよそ 5 分の 1 に縮め、直前のターンの辞書はコンテキストの大きさにかかわらず、およそ 1 キロバイトを残します。

cargo build --release --locked
python3 scripts/bench.py --turns 20 --context-kb 1024

やらないこと

節約するのはバイト数であり、トークンではありません。
モデルが受け取るリクエストは同じで、課金されるトークンも同じです。プロバイダーのプロンプトキャッシュは繰り返される接頭辞を処理する費用を削り、Portway はそれを送る費用を削ります。両方をお使いください。
レシーバーが必要です。
プロトコルに対応していることを通知しない API に直接向けた場合、センダーはリクエストを圧縮せずそのまま転送します。レシーバーは portway receive か、このプロトコルを実装した任意のサーバーです。
再起動すると忘れます。
辞書は両端のメモリにしか存在せず、認証情報ごとに分かれています。既定では 32 KiB 未満のボディが辞書になることはありません。
話すのは素の HTTP/1.1 です。
WebSocket も CONNECT も HTTP/2 も受信側 TLS もありません。TLS と認証は手前のゲートウェイに任せてください。リクエストは設定可能な 256 MiB までバッファリングし、応答はストリーミングします。
