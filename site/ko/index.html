에이전트는 매 턴 대화 전체를 다시 보냅니다.

Portway는 달라진 부분만 보내는 로컬 HTTP 프록시입니다. 링크 반대편에 Portway 수신기를 두면 각 요청은 직전 요청에 대한 델타로 네트워크를 건넙니다. 세션이 아무리 길어져도 약 1킬로바이트입니다.

GitHub에서 소스 보기 시작하기

40턴은 39턴 더하기 4킬로바이트

코딩 에이전트는 서버에 아무 상태도 남기지 않습니다. 다음 한 걸음을 내딛으려면 시스템 프롬프트와 이전의 모든 메시지, 모든 도구 실행 결과를 다시 보내고, 그 뒤에 새로 생긴 몇 킬로바이트를 덧붙입니다. 그러니 각 요청은 직전 요청을 거의 그대로 복사한 것입니다.

그래서 세션의 업로드량은 길이의 제곱으로 늘어납니다. 그 업로드가 기다림이나 비용으로 돌아오는 곳에서는 금세 눈에 띕니다:

  • 다른 리전에 있는 자체 구동 모델 서버나 직접 운영하는 게이트웨이,
  • 매 턴이 VPN이나 SSH 홉을 건너야 하는 원격 개발 머신,
  • 느리거나 공유된, 혹은 종량제 회선을 쓰는 노트북.

짧은 단발 요청에서는 얻을 게 거의 없습니다. 기반으로 삼을 앞선 요청이 없기 때문입니다.

직전 턴이 사전이 됩니다

Portway는 두 곳에서 실행됩니다. 에이전트 옆의 송신기와, 에이전트가 호출하는 서비스 앞의 수신기입니다. 양쪽 모두 마지막으로 합의한 요청 본문을 보관합니다. 송신기는 다음 요청을 그 본문에 대해 압축하고, 수신기는 서비스가 바이트 하나라도 보기 전에 원본을 복원합니다.

양쪽이 기반을 합의하는 방법

  1. 1턴이 사전을 심습니다. 이 요청은 zstd로 압축되어 X-Dict-Store: 1과 함께 전송됩니다. 수신기는 이를 복원해 넘겨주고 본문을 보관합니다.

  2. 수신기는 보관한 것을 확인해 줍니다. 응답에 실제로 저장한 바이트의 SHA-256을 담은 X-Dict-Stored가 실립니다. 송신기는 그 해시가 자기 사본과 일치할 때만 그 본문을 기반으로 씁니다.

  3. 2턴은 1턴을 해시로 지목합니다. DCZ로 전송됩니다. 사전의 SHA-256을 담은 40바이트 헤더 뒤에, 그 사전에 대해 압축되고 체크섬이 붙은 zstd 프레임이 이어집니다. 송신기는 라우트마다 확인된 본문을 최대 여덟 개까지 보관하고, 새 요청과 가장 긴 접두사를 공유하는 것을 고릅니다. 추가만 되는 대화에서는 그것이 직전 턴입니다.

기반이 사라지면 단계적으로 물러섭니다

수신기가 재시작하거나, 오래된 본문을 밀어내거나, 처음 보는 송신기를 만날 수 있습니다. 어느 경우에도 요청은 실패하지 않습니다. 수신기는 복원할 수 없는 요청을 애플리케이션이 실행되기 전에 거부하고 거부 표시를 남기며, 송신기는 더 낮은 압축으로 다시 시도합니다.

  1. 보관된 본문에 대한 DCZ 412 사전 없음, 또는 400·415 프레임 거부 시 물러섬
  2. 사전 없는 순수 zstd 415 인코딩 거부 시 물러섬
  3. 압축 없이, 에이전트가 보낸 그대로 항상 허용됨

요청은 최대 세 번 전송됩니다. Portway는 수신기의 표시가 붙은 거부만 재생하고, 수신기는 애플리케이션 응답에서 그 표시를 제거합니다. 따라서 애플리케이션이 재생을 유발할 수 없고 요청을 두 번 실행하지도 않습니다. 애플리케이션이 낸 오류는 그대로 에이전트에게 돌아갑니다.

한 턴의 비용은 그 턴이 더한 만큼입니다

같은 벤치마크를 네 가지 컨텍스트 크기로, 각각 스무 턴씩 돌렸습니다. 순수 zstd는 요청을 약 5분의 1로 줄이고, 직전 턴 사전은 컨텍스트가 아무리 커도 약 1킬로바이트를 남깁니다.

첫 턴을 뺀, 턴당 회선 전송 바이트
1턴의 컨텍스트 비압축 zstd만 Portway 20턴 동안 절감
128 KiB175,40541,9621,10498.5%
256 KiB306,50369,6081,05898.7%
512 KiB570,438122,0891,03498.8%
1 MiB1,094,276222,9371,04898.9%

마지막 열은 사전을 심으려고 컨텍스트 전체를 나르는 첫 요청을 포함합니다. 합성 텍스트는 순수 zstd가 Portway 자신의 소스에서만큼 절감하도록 맞춰 두었습니다. 모든 실행은 바이트 단위로 재현되며, 복원된 본문은 보낸 바이트의 SHA-256과 대조됩니다.

cargo build --release --locked
python3 scripts/bench.py --turns 20 --context-kb 1024

하지 않는 일

바이트를 절약합니다. 토큰이 아닙니다.
모델은 동일한 요청을 받고 동일한 토큰을 청구합니다. 프로바이더의 프롬프트 캐싱은 반복되는 접두사를 처리하는 비용을 줄이고, Portway는 그것을 보내는 비용을 줄입니다. 둘을 함께 쓰십시오.
수신기가 필요합니다.
프로토콜을 광고하지 않는 API에 그대로 겨누면 송신기는 요청을 압축하지 않고 그대로 전달합니다. 수신기는 portway receive이거나, 프로토콜을 구현한 아무 서버입니다.
재시작하면 잊습니다.
사전은 양쪽 모두 메모리에만 있고, 자격 증명별로 분리됩니다. 기본적으로 32 KiB 미만의 본문은 사전이 되지 않습니다.
평범한 HTTP/1.1로 말합니다.
WebSocket도 CONNECT도 HTTP/2도 인바운드 TLS도 없습니다. TLS와 인증은 앞단의 게이트웨이가 맡으십시오. 요청은 설정한 최대 256 MiB까지 버퍼링하고, 응답은 스트리밍합니다.

사용해 보기

macOS나 Linux에서 Rust 1.97 이상과 C 툴체인이 필요합니다. 프로바이더도 엔드포인트도 자격 증명도 가격도 어느 것 하나 내장되어 있지 않습니다.

  1. 체크아웃에서 설치합니다. 터미널 대시보드와 브라우저 콘솔까지 쓰려면 --features tui,web을 붙입니다.

    git clone https://github.com/rath/portway
cd portway
cargo install --path crates/portway --locked

  2. 서비스를 가리키고 실행합니다.

    # portway.toml
upstream = "https://api.example.com"
host = "127.0.0.1"
port = 8787
    portway --config ./portway.toml

  3. 에이전트를 Portway로 향하게 합니다. API base URL을 http://127.0.0.1:8787/v1로 바꾸고 키와 모델 이름은 그대로 둡니다. Portway는 Authorization 헤더를 그대로 넘겨주며 자체 키를 갖지 않습니다.

  4. 반대편에 수신기를 둡니다. 서비스 앞의 게이트웨이 뒤에서 portway receive를 실행한 다음, 송신기가 그 게이트웨이를 향하도록 설정합니다. 수신기 설정 에 과정이 나와 있습니다.

같은 저장소에 임베드할 수 있는 Rust 라이브러리 portway-core와, 데몬 모드와 리포트, 터미널 대시보드, 브라우저 콘솔을 갖춘 CLI가 함께 들어 있습니다. 요청 메타데이터만 SQLite에 기록하며, 본문과 자격 증명, 사전 내용은 기록하지 않습니다.
