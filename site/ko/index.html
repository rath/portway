에이전트는 매 턴 대화 전체를 다시 보냅니다.

Portway는 달라진 부분만 보내는 로컬 HTTP 프록시입니다. 링크 건너편에 Portway 수신기를 두면, 각 요청은 직전 요청 대비 델타로 네트워크를 건너갑니다. 세션이 아무리 길어져도 약 1킬로바이트입니다.

GitHub에서 소스 보기 시작하기

40턴은 39턴 더하기 4킬로바이트

코딩 에이전트는 서버에 아무 상태도 남기지 않습니다. 한 단계 더 나아가려면 시스템 프롬프트와 앞서 오간 모든 메시지, 모든 도구 실행 결과를 다시 보내고, 그 뒤에 새로 생긴 몇 킬로바이트를 덧붙입니다. 그러니 각 요청은 직전 요청을 거의 그대로 복사한 것입니다.

그래서 세션의 업로드량은 길이의 제곱에 비례해 늘어납니다. 그 업로드가 곧 기다림이거나 비용이 되는 환경에서는 금세 드러납니다:

  • 다른 리전에 있는 자체 호스팅 모델 서버나 직접 운영하는 게이트웨이,
  • 매 턴마다 VPN과 SSH 구간을 지나야 하는 원격 개발 머신,
  • 느리거나, 여럿이 나눠 쓰거나, 종량제인 회선에 연결된 노트북.

짧은 단발 요청에서는 얻을 게 거의 없습니다. 기준 삼을 앞선 요청이 없기 때문입니다.

직전 턴이 사전이 됩니다

Portway는 두 곳에서 실행됩니다. 에이전트 옆의 송신기와, 에이전트가 호출하는 서비스 앞의 수신기입니다. 양쪽 모두 마지막으로 합의한 요청 본문을 보관합니다. 송신기는 그 본문을 기준으로 다음 요청을 압축하고, 수신기는 서비스가 바이트 하나라도 보기 전에 원본을 그대로 되돌립니다.

양 끝이 기준을 합의하는 방법

  1. 1턴이 사전의 씨앗을 뿌립니다. 이 요청은 zstd로 압축해 X-Dict-Store: 1과 함께 보냅니다. 수신기는 압축을 풀어 넘겨주고, 본문은 보관합니다.

  2. 수신기는 무엇을 보관했는지 알려 줍니다. 응답에는 실제로 저장한 바이트의 SHA-256을 담은 X-Dict-Stored가 붙습니다. 송신기는 그 해시가 자기 사본과 일치할 때만 그 본문을 기준으로 삼습니다.

  3. 2턴은 1턴을 해시로 지목합니다. DCZ 형식으로 나갑니다. 사전의 SHA-256을 담은 40바이트 헤더 뒤에, 그 사전을 기준으로 압축되고 체크섬으로 끝나는 zstd 프레임이 이어집니다. 송신기는 라우트마다 확인된 본문을 최대 여덟 개까지 보관하고, 새 요청과 접두사를 가장 길게 공유하는 본문을 고릅니다. 앞에 덧붙이기만 하는 대화라면 그것이 직전 턴입니다.

기준이 사라지면 한 단계씩 물러섭니다

수신기가 재시작하거나, 오래된 본문을 밀어내거나, 처음 보는 송신기를 만날 수 있습니다. 어느 쪽이든 요청이 실패하지는 않습니다. 수신기는 복원할 수 없는 요청을 애플리케이션이 실행되기 전에 거부하고 거부했다는 표식을 남기며, 송신기는 압축을 낮춰 다시 시도합니다.

  1. 보관된 본문을 기준으로 한 DCZ 412 사전이 사라졌거나 400·415로 프레임이 거부되면 물러납니다
  2. 사전 없이 zstd만 415로 인코딩이 거부되면 물러납니다
  3. 압축 없이, 에이전트가 보낸 그대로 항상 받아들여집니다

요청은 아무리 많아도 세 번까지만 나갑니다. Portway가 다시 보내는 것은 수신기의 표식이 붙은 거부뿐이고, 수신기는 애플리케이션 응답에서 그 표식을 지웁니다. 그래서 애플리케이션 때문에 재전송이 일어날 수 없고, 같은 요청이 두 번 실행되는 일도 없습니다. 애플리케이션이 낸 오류는 그대로 에이전트에게 돌아갑니다.

한 턴의 비용은 그 턴이 더한 만큼입니다

같은 벤치마크를 네 가지 컨텍스트 크기로, 각각 스무 턴씩 돌렸습니다. zstd만으로 압축하면 요청이 약 5분의 1로 줄고, 직전 턴 사전을 쓰면 컨텍스트가 아무리 커도 약 1킬로바이트만 나갑니다.

첫 턴을 빼고, 턴마다 회선으로 나간 바이트
1턴의 컨텍스트 비압축 zstd만 Portway 20턴 동안 절감
128 KiB175,40541,9621,10498.5%
256 KiB306,50369,6081,05898.7%
512 KiB570,438122,0891,03498.8%
1 MiB1,094,276222,9371,04898.9%

마지막 열은 사전의 씨앗을 뿌리려고 컨텍스트 전체를 나르는 첫 요청까지 포함합니다. 합성 텍스트는 zstd만 써도 Portway 자신의 소스에서와 비슷한 절감률이 나오도록 맞춰 두었습니다. 모든 실행 결과는 바이트 단위까지 똑같이 재현되고, 복원된 본문은 보낸 바이트의 SHA-256과 대조해 검증합니다.

cargo build --release --locked
python3 scripts/bench.py --turns 20 --context-kb 1024

하지 않는 일

바이트를 절약합니다. 토큰이 아닙니다.
모델이 받는 요청은 똑같고, 청구되는 토큰도 똑같습니다. 프로바이더의 프롬프트 캐싱은 반복되는 접두사를 처리하는 비용을 줄이고, Portway는 그 접두사를 보내는 비용을 줄입니다. 둘을 함께 쓰면 됩니다.
수신기가 필요합니다.
프로토콜 지원을 알리지 않는 API에 바로 연결하면, 송신기는 요청을 압축하지 않고 그대로 넘깁니다. 수신기는 portway receive이거나, 이 프로토콜을 구현한 아무 서버나 됩니다.
재시작하면 잊습니다.
사전은 양쪽 메모리에만 존재하고, 자격 증명마다 따로 둡니다. 기본 설정에서는 32 KiB 미만의 본문이 사전이 되지 않습니다.
평범한 HTTP/1.1만 씁니다.
WebSocket도 CONNECT도 HTTP/2도 인바운드 TLS도 없습니다. TLS와 인증은 앞단의 게이트웨이에 맡기면 됩니다. 요청은 설정값에 따라 최대 256 MiB까지 버퍼링하고, 응답은 스트리밍합니다.

사용해 보기

macOS나 Linux에서 Rust 1.97 이상과 C 툴체인이 필요합니다. 프로바이더도 엔드포인트도 자격 증명도 가격도 어느 하나 내장돼 있지 않습니다.

  1. 저장소를 받아 설치합니다. 터미널 대시보드와 브라우저 콘솔까지 쓰려면 --features tui,web을 붙입니다.

    git clone https://github.com/rath/portway
cd portway
cargo install --path crates/portway --locked

  2. 벤더의 API를 이름으로 마운트하고 실행합니다.

    # portway.toml
host = "127.0.0.1"
port = 8787

[upstreams]
anthropic = "https://api.anthropic.com"
codex = "https://chatgpt.com/backend-api/codex"
    portway --config ./portway.toml

  3. 에이전트를 자기 마운트로 향하게 합니다. 바꿀 것은 그것뿐입니다. Claude Code는 ANTHROPIC_BASE_URL=http://127.0.0.1:8787/anthropic, Codex는 프로바이더 항목의 base_url = "http://127.0.0.1:8787/codex"입니다. 로그인과 모델 이름은 각자 그대로 쓰고, Portway는 요청에 실린 자격 증명을 그대로 넘겨주며 키를 따로 갖지 않습니다. OpenAI 호환 서비스라면 upstream 하나와 base URL http://127.0.0.1:8787/v1이면 됩니다.

  4. 건너편에 수신기를 둡니다. 서비스 앞의 게이트웨이 뒤에서 portway receive를 돌린 다음, 송신기가 그 게이트웨이를 바라보게 설정합니다. 수신기 설정에 과정이 나와 있습니다.

같은 저장소에는 임베딩할 수 있는 Rust 라이브러리 portway-core와, 데몬 모드·리포트·터미널 대시보드·브라우저 콘솔을 갖춘 CLI가 같이 들어 있습니다. 요청 메타데이터만 SQLite에 기록하고, 본문과 자격 증명, 사전 내용은 기록하지 않습니다.
